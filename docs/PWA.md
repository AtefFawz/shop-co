# Progressive Web App

SHOP.CO includes the foundations of an installable Progressive Web App (PWA). On supported browsers, customers can add the site to their home screen and launch it in a standalone app window.

## Included capabilities

- Web app manifest generated by `src/app/manifest.ts`.
- 192px, 512px, maskable, and Apple touch icons in `public/icons/`.
- Standalone display mode and shortcuts to the shop and order history.
- A custom install prompt with browser-specific guidance.
- A launch screen for the installed experience.
- A service worker at `public/sw.js`.
- A lightweight offline page at `public/offline.html`.

## Offline behavior

The service worker caches the offline page and application icons during installation. Selected static assets are cached as they are requested. When a navigation request fails, the worker can return the offline page.

The worker deliberately excludes API, authentication, checkout, and order paths from caching. This prevents private or stale transactional data from being served as if it were current. The app does not support offline checkout or offline account/order management.

## Notifications

The notification inbox and live updates use the backend API and Socket.IO when configured. If the user grants notification permission, an update received over an active Socket.IO connection can be displayed as a system notification while the page is in the background.

The service worker also contains a standard `push` event handler. However, push delivery while the app is fully closed is not complete until the backend implements all of the following:

1. VAPID key generation and secure storage of the private key.
2. An authenticated endpoint to create, update, and remove browser push subscriptions.
3. Storage of each subscription against the correct user account.
4. Server-side push delivery when relevant events occur, such as an order status change.
5. Expired-subscription handling and delivery failure cleanup.

Never expose a VAPID private key or other server secret through a `NEXT_PUBLIC_*` variable.

## Browser permissions

The app asks for notification permission only after a user action. It does not request camera, microphone, or location access as part of the shopping flow. In addition, the current `Permissions-Policy` response header disables camera, microphone, geolocation, and payment browser features. Review and update that policy deliberately before adding a feature that needs one of those APIs.

## Install and test

PWA installation and service workers require a secure context in normal deployment. Use HTTPS in staging and production. Browsers generally treat `localhost` as a secure development origin.

- **Android:** open the site in a supported browser and use its Install app or Add to Home screen action.
- **iPhone/iPad:** open the site in Safari, choose Share, then Add to Home Screen.
- **Desktop:** use the browser's install option when it is offered.

The application registers the service worker in production mode. A normal `next dev` session is useful for UI development, but it does not exercise the same service-worker lifecycle as a production build. For an end-to-end PWA check, create a production build and serve it over HTTPS or localhost, then inspect the manifest and service worker in browser developer tools.

## Limitations

A PWA is still a web application. Browser and operating-system support determines which device APIs are available; it does not receive every permission or background capability available to a native Android or iOS application. The current implementation does not provide offline commerce or full Web Push delivery while closed.
